## Verdict — what is and is not proven

* NOT proven: a human double-click duplicating the transition. The
  `isSubmitting` state guard + `disabled={isSubmitting || …}`
  (`src/components/modals/ApplicationDetailModal.tsx:82-85`, `:215`, `:218`) holds for any two
  clicks separated by a task boundary, which is what a real double-click is. Recording this
  openly: D-08a needed three synthetic same-task dispatches.
* PROVEN (D-08a): the guard is render-state only — there is no synchronous re-entrancy flag
  (`useRef`) and no idempotency key on the write. Any caller that reaches `runTransition` twice
  before React commits appends two audit rows while the case file records one transition. The two
  representations of the same statutory decision are written by different mechanisms and diverge
  by construction; nothing reconciles them.
* PROVEN (D-08a): the duplication is user-visible in the trail a Super Admin reads, and the page
  caption advertises `evidence/raw/D08_double_submit_audit_rows.txt` ->
  `src/data/platformKnowledgeBase.ts:45` "Cryptographically signed audit trail recording every
  approval decision".
* SUSPECTED, must be confirmed in Pass C (probe **P-04**): the realistic trigger in `postgres`
  mode is a *retried request*, not a retried click — `POST /api/applications/:id/transition`
  carries `expectedVersion` (`ApplicationDetailModal.tsx:98`) but no idempotency key, so a client
  or proxy retry after a lost response writes a second audit row for one decision. Confirm by
  replaying the same transition POST twice and reading `auditLogs`.

Severity intent for the report: **P2** (integrity/design, real trigger unproven in demo mode),
upgradable to P1 if P-04 shows the server appends the audit row before or independently of the
version check.
