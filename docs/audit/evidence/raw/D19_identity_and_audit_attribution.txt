(4) P1 — the audit trail has no sortable, second-resolution timestamp in either mode.
    prisma/schema.prisma:255-276
      model AuditLog { timestamp String   // :257
                       @@index([timestamp]) }   // :272
    The value written is a display string (server/audit.ts:16-21 + :26
      `timestamp: formatAuditTimestamp()`) -> "01 Nov 2026, 10:39 PM":
      - minute resolution only; events in the same minute are unordered,
      - day+month+year as text, so SQL ORDER BY / BETWEEN and the :272 index are useless
        (lexicographic order puts "01 Nov" before "15 Oct"),
      - no timezone, no ISO instant.
    The server has already worked around it: server/routes/data.ts:491 sorts notifications by the
    same text column, while :499 reads the audit trail with `orderBy: { id: 'desc' }` — i.e. the
    trail's ordering depends on the id format, which itself differs per mode
    (client 'AUD-<decimal-ms>-<rand>' vs server 'LOG-<base36-ms>-<hex>'). That is why the D-08
    duplicate-row analysis had to fall back to array order instead of timestamps.
    Related: data.ts:499 also caps the trail at `take: 200` with no total, cursor or "showing the
    most recent 200 of N" affordance, so an officer reading a long case history sees a silent
    truncation.
    Fix: add `occurredAt DateTime @db.Timestamptz(3)` (+ keep the display string if the UI needs
    it), index that, order by it, and page the trail. This is a migration — the audit prompt
    requires stopping for approval before a destructive migration, and this one is additive,
    so it belongs in the Wave plan with an explicit backfill step. Effort M.

(5) P3 — the demo "session token" is security theatre, and one fabricated field is exported.
    Read from the browser 2026-11-02; the three token segments are REDACTED here before commit
    (see evidence/probe-log.md "Redactions"), the structure and the decoded payload are verbatim:
      document.cookie =
        apoorvasetu_session_token=<REDACTED-JWT: header>.<REDACTED-PAYLOAD>.<REDACTED-SIGNATURE>
      plus apoorvasetu_refresh_token=<REDACTED-REFRESH-TOKEN>
      decoded payload of the middle segment: {"sub":"USR-SUPERADMIN","sid":"SID-MVY2L2SB-BZ4W7A",
        "exp":1793553855131}
    - The cookie is written by JavaScript (src/services/authService.ts:31-40 setCookie) so it is
      readable by any script on the page: no HttpOnly on the demo path (the Postgres path uses the
      HttpOnly apoorvasetu_sid cookie — confirmed in evidence/raw/S28_live_headers_demo.txt).
    - The third segment is a 16-hex-char string ("5d6694cf35472a02"), not a base64url HMAC of the
      first two segments, so it is a JWT-shaped value that no verifier would accept — while the
      "production" HMAC key that purports to sign it is embedded in the bundle (src/services/authService.ts:28, see evidence/raw/S22b_served_bundle_greps.txt).
      Together: the demo advertises cryptography it does not perform, and ships the key for the
      forgery it does not perform. Filed under L4 (AUD for L4-02); this probe confirms the shape.
    - The demo session records `"ipAddress": "10.24.1.84"` — a hard-coded fiction that lands in
      the audit CSV's IP column. Server default is '127.0.0.1' (server/audit.ts:24,47) with
      clientIp(req) passed on workflow routes (server/routes/workflow.ts:110); a demo row that
      invents a routable-looking client IP is worse than a blank, because the export looks
      evidentiary.
    Fix: for demo mode, stop minting a JWT-lookalike and the fake IP (record "demo" or omit the
    column), and move the secret to the server (already required by L4-02). Effort S.
