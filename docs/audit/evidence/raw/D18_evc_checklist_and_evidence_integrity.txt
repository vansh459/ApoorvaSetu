(4) P2 — the claim on the screen is stronger than the mechanism.
    src/pages/evc/EvidenceUpload.tsx:66
      <span className="text-xs text-ink-2">Tamper-proof attachments</span>
    and :140 "Records added here are listed in the signed report."
    What actually exists: an array of strings on the visit row. In demo mode the entry is only the
    file name — src/pages/evc/EvidenceUpload.tsx:38-41
      if (!isFileUploadEnabled()) { addVisitEvidence(visit.id, file.name); return; }
    no bytes, no size, no hash, no uploader identity, no timestamp, and no success toast (the
    toast is only on the remote branch at :47). In Postgres mode the value is the storage key
    (:46 uploaded.key), which is content-addressed only if the bucket versioning/ACL does it —
    nothing in this repo signs or digests the object. A deletable, unhashed string list is
    tamper-*evident* at best through the audit row, never tamper-proof.
    Same category as the knowledge-base claim already filed in L9:
    src/data/platformKnowledgeBase.ts:45 "Cryptographically signed audit trail recording every
    approval decision" — see evidence/raw/S17_audit_chain.txt (append-only API but no chain
    digest) — so the product states a guarantee in two places that the data model does not hold.
    Fix: either implement it (store digest + uploader + attach time per evidence item and add an
    `guard` on evcSpec that rejects shrinking evidenceFiles/checklist outside
    evc.report.submit) or reword the two captions to what the system does
    ("attachments are recorded in the audit trail; removal requires report unlock"). Effort M for
    the implementation, S for the reword.
